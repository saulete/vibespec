# VibeSpec

**English** | [Español](README.es.md)

Rigorous product development framework for vibe coders and small teams. 4 skills, 1 hook, 0 bureaucracy.

*Magnifique, Fantastique, VibeSpec!*

---

## Why this exists

VibeSpec was born from an article: [Cómo unimos producto e ingeniería con agentes en Mercadona Tech](https://www.gemba.es/p/como-unimos-producto-e-ingenieria), written by [José Ramón Pérez Agüera](https://www.gemba.es) on [Gemba](https://www.gemba.es). Their GSD → Mercadona User Story Toolkit → Superpowers pipeline proved that agents can mechanize rigor without mechanizing bureaucracy — for teams of 5-12 people with separate PM and Engineering roles.

But for vibe coders and small teams, that ceremony is a wall: 79 commands, 22 skills, 34 agents, 12 hooks, 8+ planning files, and 250-500k tokens per medium feature.

**VibeSpec is a simplified version of that pipeline:** same discipline (Working Backwards, TDD, spec drift detection, anti-waterfall batches), less ceremony (1 spec instead of 8 files, 4 skills instead of 79 commands, 0 bridges to synchronize). Built for vibe coders and small teams who want rigor without overhead. Without José and Gemba, this framework would not exist.

---

## The 7 rigor principles (non-negotiable)

These principles come from the original article and Amazon's Working Backwards. They are not removed — they are simplified.

| Principle | In Mercadona pipeline | In VibeSpec |
|---|---|---|
| **Working Backwards** | PROJECT.md + REQUIREMENTS.md + ROADMAP.md + SPEC.md + PLAN.md | 2-3 sentences in SPEC.md |
| **Falsifiable Acceptance Criteria** | 6D Scoring (0-10) + quality gate ≥7 | "Can you write a test for this?" |
| **TDD** | Superpowers test-driven-development skill | Same — red → green → refactor |
| **Anti-Waterfall** | 5-lens weighted prioritization + batches | Batches that deliver independent value |
| **Verification** | gsd-verify-work + gsd-bridge + VERIFICATION.md | verify skill + VERIFICATION.md |
| **Traceability** | REQ-IDs in commits + gsd-bridge sync | SC-IDs in commits + hook auto-sync |
| **Spec Drift Detection** | gsd-bridge amend + SPEC-AMENDMENTS.md | Amendments in SPEC.md without overwriting |

## What gets removed and why

### Bureaucracy that only makes sense when PM and Eng are separate roles

| Element | Exists for | Why it's unnecessary for small teams |
|---|---|---|
| Formal PRD with GAP detection | PM → Eng handoff | You are both |
| Mom Test interviews + field notes | Quantitative/qualitative research | You talk to users directly or you are the user |
| JTBD with 3 motivations + Wendel Checklist | Methodological PM | The "job" is captured in 1-2 sentences |
| 6D Scoring (0-10) | Quality gate between roles | You trust your judgment + tests |
| 5-lens Weighted Prioritization | Backlog with 20+ stories competing | You prioritize by value+learning |
| gsd-bridge.py (438 lines) | Syncing GSD ↔ Superpowers | Single tool, no gap |
| 65 commands / 33 agents / 12 hooks | Multi-role coordination | Total overkill |
| `.planning/` with 8+ files | Audit trail between departments | SPEC.md + context.md is enough |
| PRDs with Farola/Penumbra | PM needing formal evidence | You have the context in your head |

### How discipline is maintained without ceremony

- **The quality gate is not a score.** It's a question: *"Can you write a test that verifies this criterion?"* If the answer is no, the criterion gets rewritten. More direct, equally rigorous.
- **Prioritization is not 5 lenses.** It's ordering features by the value they deliver to the user, and shipping in batches that work on their own. If a batch doesn't deliver value without the next one, it's badly divided.
- **The roadmap is not ROADMAP.md.** It's an ordered list in `context.md` that you reorder when you learn something new. A `???` is as valid as a defined feature — it means "I have an intuition, I need to see what happens."
- **The bridge is not 438 lines of Python.** It's a hook that marks SC-IDs as complete in SPEC.md when it detects them in commits. Single source of truth, no synchronization.

## Project structure

```
my-project/
├── .vibespec/
│   ├── context.md              ← STABLE: product, stack, conventions, features list
│   ├── archive/                ← Completed features
│   │   └── 001-reading-list/
│   │       ├── SPEC.md
│   │       └── VERIFICATION.md
│   └── PLAN.md                 ← Auto-generated by /build
├── SPEC.md                     ← Active feature (always in root)
└── src/                        ← Your code
```

### context.md — What doesn't change

```markdown
# Project: ReadTrack

## What it is
Personal reading list app where users organize books, track progress and discover new reads.

## Stack
- Frontend: Next.js 15 + React 19 + Tailwind CSS
- Backend: Next.js API routes
- Database: PostgreSQL via Drizzle ORM
- Testing: Vitest

## Features (ordered by priority)
1. reading-list — Create lists, add books, track progress, see recommendations
2. ???

## Conventions
- Commits: Conventional Commits with SC-ID
- TDD mandatory in production code
- p95 < 500ms on API endpoints
```

Written once. Updated when:
- You learn something that changes feature priorities
- The stack changes
- A new convention is added

### SPEC.md — The active feature

```markdown
# Feature: reading-list

## Working Backwards
When done, users can save books to custom lists, mark reading progress,
and see recommendations based on their lists. We'll know it works because
creating a list and adding 3 books produces at least 5 relevant suggestions.

## For Whom
Readers who read 10+ books a year and waste time figuring out what to read next.

## Success Criteria (falsifiable)
- [ ] SC-01: User can create list with name and visibility (public/private)
- [ ] SC-02: Search returns results in <300ms with 3+ results for queries ≥3 chars
- [ ] SC-03: Reading progress updates without page reload (not started, reading, done)
- [ ] SC-04: Recommendations show at least 5 books, 3+ share genre with user's lists

## Out of Scope
- Reviews and ratings — separate feature
- Import lists from Goodreads — doesn't validate the core hypothesis

## Batches (anti-waterfall)
### Batch 1: Lists and books
- Implements: SC-01, SC-02
- Value: Users can create lists and add books
### Batch 2: Progress and recommendations
- Implements: SC-03, SC-04
- Value: Users track reading and discover new books

## Amendments
- AMEND-01: [abc123f] SC-02 requires minimum 3 chars to activate search,
  1-2 chars return noise — 2026-05-04
```

**Amendments are the trace of spec drift.** The original Success Criteria is never overwritten — an amendment is added explaining what changed and why. This preserves the trail, like SPEC-AMENDMENTS.md in the original pipeline.

## The 4 skills

### `/spec` — Think before you code

Replaces: GSD new-project + discuss-phase + plan-phase + MUST prd-quality-guard + from-gsd + research

1. If no `context.md` → asks and creates it (product, stack, conventions, features list)
2. If `context.md` exists without SPEC.md → suggests the next feature from the list
3. Asks Working Backwards questions until the idea is understood
4. **Forces falsifiable Success Criteria** — refuses to accept "improve UX" or "make it faster"
5. Proposes anti-waterfall batches and verifies each batch delivers independent value
6. Writes SPEC.md in the project root

### `/build` — Build with TDD

Replaces: Superpowers writing-plans + subagent-driven-development + test-driven-development + GSD execute-phase

1. Reads SPEC.md + context.md
2. Decomposes the current batch into atomic tasks (2-5 min each)
3. Each task: **red test → minimal implementation → green test → refactor**
4. Commits with SC-ID: `feat: implement SC-01 ambiguity classifier`
5. When batch is complete, invokes `/verify` automatically

**Iron rules:**
- NO production code without a failing test first
- NO completion claims without fresh verification evidence
- Delete code written before tests

### `/verify` — Prove it works

Replaces: GSD verify-work + gsd-bridge + MUST quality validation

1. Runs tests → green?
2. Verifies each Success Criteria → PASS/FAIL
3. Compares code vs SPEC.md → detects drift
4. If divergence → adds Amendments to SPEC.md (never overwrites)
5. Generates `.vibespec/VERIFICATION.md`

### `/iterate` — Next batch, next feature

Replaces: GSD complete-milestone + new-milestone + next + MUST prioritize

1. Shows status: completed batches, done SCs, what's left
2. If remaining batches in active feature → next batch
3. If feature is complete → archives SPEC.md + VERIFICATION.md to `.vibespec/archive/`
4. Reads `context.md` → "Next feature: reading-list. Continue or reorder?"
5. If reorder → updates the features list in context.md

---

## The hook

### `vibespec-sync` (PostSessionEnd)

Replaces: gsd-bridge sync

- If SPEC.md exists → scans commits since last verification
- Extracts SC-IDs from commit messages
- Marks Success Criteria as `[x]` in SPEC.md
- If all SCs in a batch are done → marks batch as complete
- Adds Amendments if it detects changes not reflected in spec

## Philosophy

**Copilot mode, not autopilot.** (From the Mercadona User Story Toolkit — we keep this.)

The framework guides you, forces you to think, blocks the vague. But it doesn't invent for you. If a metric is missing, the skill tells you and asks you to define it. If a Success Criteria isn't falsifiable, it makes you rewrite it. If a batch doesn't deliver value on its own, it makes you reorganize.

**Discipline lives in the questions, not in the forms.**
